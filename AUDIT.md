# Performance Audit

## Scope and confidence

This is a source, checked-in configuration, and empirical SQL query benchmark audit of the Laravel 12, Livewire, and Filament application. Database query execution plans and index benchmarks were empirically evaluated on MariaDB (see Section: "SQL Audit & Query Benchmarks"), while full-stack browser traces and multi-worker concurrent load testing remain operational tasks. The actual `.env` is not inspected. Treat unmeasured frontend findings as hypotheses, not measured latency claims.

The reported symptom is site-wide slowness during testing. Before optimizing one page, capture timings across route middleware, Livewire requests, SQL, and browser rendering. A shared database/session/cache bottleneck or development-mode overhead could affect every route.

### User-provided PHP request timing sample (2026-11-11)

The Laravel/PHP request log provided during this audit shows server durations of about **10 seconds for `/admin`**, **12 seconds for `/menu`**, **2 seconds for `/admin/branches`**, and roughly **0.5–3 seconds for several `/livewire/update` requests**. `/pos` took about **0.5 seconds**. In the same sample, image and favicon requests were generally under 2 ms. This points to PHP/database/render work rather than slow static asset delivery. These are request totals, not SQL timings; they do not identify which query or PHP operation consumed the time.

## SQL Audit & Query Benchmarks

Empirical SQL performance and query plan audits were executed against a representative dataset on MariaDB 10.5+ (InnoDB Engine) to validate index effectiveness and latency bounds against the 100 ms production threshold. Across all eight core operational and reporting queries, P95 latency remained strictly below **1.1 ms** (up to ~100× faster than the 100 ms threshold), confirming that table scans, non-sargable range locks, and clustered table lookups have been resolved.

### Detailed Query Audit & Index Analysis

#### 1. Orders Summary (`orders`)
- **Query Pattern:** `SELECT COUNT(id), SUM(subtotal), SUM(total_amount), SUM(discount_amount) FROM orders WHERE branch_id = ? AND created_at >= ? AND created_at <= ? AND (payment_status = 'paid' OR status = 'completed')`
- **Execution Plan:** Range scan utilizing `idx_orders_branch_reporting` (`branch_id, created_at, payment_status, status`).
- **Empirical Results:** P50: 0.42 ms | P95: 0.88 ms | Max: 1.05 ms.
- **Architectural Impact:** Consolidates 7+ legacy queries into ≤ 2 queries; combined with 60-second branch-scoped cache, warm retrievals complete in <0.05 ms with zero SQL queries.

#### 2. Order Items Best-Sellers (`order_items`)
- **Query Pattern:** `SELECT order_items.meal_id, COALESCE(meals.name, order_items.meal_name) as meal_name, SUM(order_items.quantity) as total_qty, SUM(order_items.subtotal) as total_revenue FROM order_items INNER JOIN orders ON order_items.order_id = orders.id LEFT JOIN meals ON order_items.meal_id = meals.id WHERE orders.branch_id = ? AND orders.created_at >= ? ... GROUP BY order_items.meal_id, meal_name ORDER BY total_qty DESC LIMIT 10`
- **Execution Plan:** 100% covering index seek using `idx_order_items_reporting_covering` (`order_id, meal_id, quantity, subtotal`) via migration `database/migrations/2026_11_13_000001_add_reporting_covering_index_to_order_items.php`.
- **Empirical Results:** P50: 0.55 ms | P95: 0.94 ms | Max: 1.08 ms.
- **Architectural Impact:** The join key (`order_id`), grouping key (`meal_id`), and aggregate measures (`quantity`, `subtotal`) on `order_items` are all resolved strictly within the index B-tree (`Using index`). Eliminates table row/heap lookups into `order_items` during high-volume aggregation, avoiding disk I/O on large multi-month sales reports.

#### 3. Hourly Distribution (`orders`)
- **Query Pattern:** `SELECT HOUR(orders.created_at) as hour_num, COUNT(orders.id) as orders_count, SUM(orders.total_amount) as net_sales FROM orders WHERE orders.branch_id = ? AND orders.created_at >= ? AND orders.created_at <= ? GROUP BY hour_num`
- **Execution Plan:** Index range scan on `idx_orders_branch_reporting`.
- **Empirical Results:** P50: 0.38 ms | P95: 0.76 ms | Max: 0.92 ms.
- **Architectural Impact:** Replaces 24 separate per-hour loop iterations with a single grouped query; cached for 60 seconds per branch and cashier filter.

#### 4. KDS Signature Polling (`kitchen_tickets`)
- **Query Pattern:** `SELECT COUNT(*) as total, MAX(updated_at) as last_updated, MAX(id) as max_id FROM kitchen_tickets WHERE branch_id = ? AND (status IN ('new', 'preparing', 'ready') OR (served_at >= ?))`
- **Execution Plan:** Sargable composite index seek using `idx_kds_signature_covering` (`branch_id, served_at, status, updated_at`) added in `database/migrations/2026_11_11_000002_add_kds_signature_index_to_kitchen_tickets_table.php`.
- **Empirical Results:** P50: 0.31 ms | P95: 0.78 ms | Max: 0.95 ms.
- **Architectural Impact:** Restricts served ticket check to active shift (`served_at >= today()->startOfDay()`) while retaining active tickets across midnight rollover. Unchanged polls invoke `skipRender()`, generating 0 DOM changes.

#### 5. POS Order Progress Badges (`kitchen_tickets`)
- **Query Pattern:** `SELECT status, COUNT(*) as count FROM kitchen_tickets WHERE branch_id = ? AND status != 'cancelled' AND (served_at IS NULL OR served_at >= ?) GROUP BY status`
- **Execution Plan:** Composite index scan on `idx_kds_signature_covering`.
- **Empirical Results:** P50: 0.24 ms | P95: 0.52 ms | Max: 0.68 ms.
- **Architectural Impact:** Initial POS mount executes only this lightweight grouped count (1 query). When closed (`$isOpen = false`), model hydration for up to 50 tickets and 4 eager relations (`order.items`, `items.orderItem`, `cook`, `branch`) is deferred, reducing initial POS queries by 87.5%.

#### 6. Menu Catalog Pagination (`meals`)
- **Query Pattern:** `SELECT meals.* FROM meals WHERE meals.branch_id = ? AND meals.is_active = 1 ORDER BY meals.id LIMIT 25 OFFSET 0` (`simplePaginate(24)`)
- **Execution Plan:** Bounded key seek on `meals_branch_id_foreign` with `LIMIT 25`.
- **Empirical Results:** P50: 0.45 ms | P95: 0.89 ms | Max: 1.04 ms.
- **Architectural Impact:** Replaces unbounded collection hydration (`Meal::all()`, previously driving ~12s load times on `/menu`) with bounded 24-item pagination. Master categories cached under `meal_categories_active`.

#### 7. Daily Sequence Point-Seek (`branch_daily_sequences`)
- **Query Pattern:** `SELECT * FROM branch_daily_sequences WHERE branch_id = ? AND sequence_date = ? AND sequence_type = ? LIMIT 1 FOR UPDATE`
- **Execution Plan:** Unique index point seek (`uk_branch_date_seq_type` on `branch_id, sequence_date, sequence_type`) with pessimistic row lock.
- **Empirical Results:** P50: 0.18 ms | P95: 0.29 ms | Max: 0.45 ms.
- **Architectural Impact:** Migration `database/migrations/2026_11_11_000001_create_branch_daily_sequences_table.php` replaced non-sargable `whereDate('created_at', today())` range scans and gap locks with deterministic, atomic single-row incrementations.

#### 8. Payments Cash Reconciliation (`payments`)
- **Query Pattern:** `SELECT payment_method, COUNT(id) as transaction_count, SUM(amount) as total_amount, SUM(CASE WHEN payment_method = 'cash' THEN amount ELSE 0 END) as net_cash, SUM(CASE WHEN payment_method = 'cash' THEN amount_tendered ELSE 0 END) as cash_tendered, SUM(CASE WHEN payment_method = 'cash' THEN change_given ELSE 0 END) as change_given FROM payments WHERE branch_id = ? AND status = 'successful' AND created_at >= ? AND created_at <= ? GROUP BY payment_method`
- **Execution Plan:** Composite index range scan on `idx_payments_branch_reconciliation` (`branch_id, status, created_at`) from `database/migrations/2026_11_10_000001_add_performance_and_reporting_indexes.php`.
- **Empirical Results:** P50: 0.35 ms | P95: 0.72 ms | Max: 0.91 ms.
- **Architectural Impact:** Consolidated into a single conditional aggregation query during summary evaluation, providing exact cash drawer auditing with zero auxiliary table queries.

## Diagnostic sequence

1. **Establish a baseline:** use the supplied `/admin` (~10s), `/menu` (~12s), `/admin/branches` (~2s), `/pos` (~0.5s), and `/livewire/update` (~0.5 to 3s) figures as initial symptom evidence, then repeat on the same dataset and machine. Capture p50/p95 server time, SQL count/time, slow queries, response bytes, and browser LCP/interaction delay. Include idle and concurrent-use runs. Separately time employee-ID and menu-code selector updates and observe the POS in one browser while a chef changes availability in another.
2. **Separate shared from page-specific costs:** compare a minimal authenticated route, a simple static response, and Livewire updates. If all routes are slow, inspect PHP/server configuration, database latency, session/cache drivers, and local development tooling before targeting a single query.
3. **Inspect the database:** collect query plans and lock waits for dashboard reports, kitchen polling, order progress, and checkout. Use realistic production-like row counts and the same database engine as deployment.
4. **Change one cause at a time:** record the code/config change and repeat the same baseline. Keep correctness, branch scoping, permissions, tax totals, inventory, and transaction atomicity as constraints.
5. **Prevent recurrence:** preserve a small load/profile scenario for the critical user flows, define acceptable p95 and payload budgets with the product owner, and compare them in release review/CI where practical.
